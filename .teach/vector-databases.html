Vector databases, under the hood

How dense vectors become searchable, why approximate nearest-neighbor indexes work, and how HNSW, inverted files, quantization, filtering, and reranking shape a production RAG system. Assumes basic familiarity with embeddings.

The system, not the label

A vector database is a database system whose retrieval path treats a vector as a first-class searchable value. The vector index is only one component. Storage, metadata indexes, mutation handling, filtering, replication, sharding, and query planning determine whether that index is useful in production.

REPRESENTATION

Embeddings

A model maps text, images, or other objects into points in a fixed-dimensional space. Geometry reflects the model's training objective, not universal meaning.

OBJECTIVE

k-nearest neighbors

Given query vector q, return the k stored vectors with best score under one chosen metric. Exact flat search is the reference answer.

ACCELERATOR

ANN index

Skip most distance computations while trying to preserve the true neighbors. “Approximate” modifies retrieval, not the vector values themselves.

Keep the layers separate. The embedding model defines the geometry. The distance metric interprets it. The ANN index approximates search over it. The database operates and filters it. A failure in one layer cannot always be fixed by tuning another.

Geometry is the contract

An index preserves rankings induced by a metric. If the embedding model expects cosine similarity but the index uses raw inner product, the system is faithfully optimizing the wrong neighborhood.

EUCLIDEAN

Squared L2

d²(x,y) = Σᵢ(xᵢ − yᵢ)²

Measures geometric separation. Squaring avoids a square root without changing rank. Faiss reports squared L2 for this reason.[2]

ANGULAR

Cosine similarity

cos(x,y) = (x·y) / (||x|| ||y||)

Compares direction while discarding magnitude. Higher is closer. Normalize both stored and query vectors when implementing cosine through inner product.

MAGNITUDE-AWARE

Inner product

s(x,y) = x·y = Σᵢxᵢyᵢ

Both direction and stored-vector norm affect ranking. Useful when magnitude carries model meaning, as in some recommendation objectives.

The normalization identity

For unit vectors, cosine, inner product, and L2 induce the same ordering:

||x − y||² = ||x||² + ||y||² − 2x·y = 2 − 2x·y

This equivalence is exact only after normalization. The query norm does not affect inner-product ranking, but each database vector's norm does.[2]

Why high dimensions change the engineering

A flat scan over N vectors of dimension d performs roughly N × d component operations per query. At one million 1,536-dimensional float32 vectors, raw vector storage alone is about 6.14 GB before IDs, graph links, metadata, allocator overhead, replicas, or indexes.

raw_vector_bytes = N * dimensions * bytes_per_component

Metric migration is an index migration. Changing embedding model, dimensionality, normalization, or distance function changes the searchable space. Store model/version metadata and rebuild into a new collection or index rather than mixing incompatible vectors.

ANN is a budgeted search

Approximate nearest-neighbor algorithms spend a controlled amount of work exploring promising regions. Their real output is a latency–recall operating point, not a universal “fast” index.

Start with exact ground truth

For a representative query set, compute exact top-k results using a flat scan. Then compare each ANN result set to that ground truth. Faiss explicitly treats IndexFlatL2 and IndexFlatIP as the exact baseline.[4]

recall@k = |ANNₖ(q) ∩ Exactₖ(q)| / k

Average recall across queries can hide failures on important slices. Break it down by tenant, language, filter selectivity, query length, corpus age, and difficult semantic categories.

QUALITY

Recall@k

How many true top-k neighbors survived candidate generation? This measures index approximation, not whether those neighbors answer the user.

SYSTEM

p50 / p95 / p99

Tail latency matters under concurrent load, cache misses, compaction, filtering, and shard fan-out. Report warm and cold behavior separately.

ECONOMICS

Memory and build cost

Track resident memory, bytes per vector, build duration, write amplification, and rebuild time. Query speed alone can choose an unaffordable design.

What “approximate” can mean

Graph pruning
Visit only a navigable subset of vectors, as in HNSW.
Space partitioning
Search only selected centroid cells, as in IVF.
Lossy scoring
Compare compressed representations, as in scalar or product quantization.
Disk-aware traversal
Arrange a graph and cache so a small number of SSD reads can reach good candidates, as in DiskANN.[7]

These techniques compose. An IVF-PQ index both skips cells and approximates distances inside them. A quantized HNSW index combines graph exploration with compressed vectors. Reranking can recover precision after either.

A defensible benchmark loop

freeze corpus snapshot + embedding model + metric
sample production-like queries and metadata filters
compute exact top-k ground truth

for index_configuration in candidate_configs:
    build from the same snapshot
    warm according to the expected deployment
    run concurrent queries at target throughput
    record recall@k, p50/p95/p99, QPS, RAM, disk, build time

choose a Pareto point, then evaluate end-to-end RAG answer quality

ANN-Benchmarks exists because different algorithms and parameter settings can yield comparable quality-performance tradeoffs; benchmark the data distribution and hardware you will operate.[5]

HNSW: navigate a hierarchy

Hierarchical Navigable Small World builds proximity graphs at several resolutions. Sparse upper layers make long jumps; the dense bottom layer refines locally. The structure resembles a geometric skip list.[3]

Construction

  1. Assign a new vector a maximum layer sampled from an exponentially decaying distribution. Most nodes exist only at layer 0; progressively fewer reach upper layers.
  2. From the current entry point, greedily descend through layers above the new node's level.
  3. At each remaining layer, run a bounded neighborhood search with candidate width efConstruction.
  4. Select up to M diverse neighbors, add bidirectional links, and prune overfull adjacency lists. Diversity prevents every edge from pointing into one dense cluster.

Query

entry = graph.entry_point

# Upper layers: greedy routing, usually one best point survives.
for level from max_level down to 1:
    entry = greedy_closest(query, entry, level)

# Base layer: best-first expansion with bounded working queues.
candidates = min_heap([entry])       # nearest unexplored first
results    = max_heap([entry])       # worst current result first
visited    = {entry}

while candidates not empty:
    current = pop_nearest(candidates)
    if distance(current, query) > distance(worst(results), query): break
    for neighbor in graph[current]:
        if neighbor not in visited and promising(neighbor, results):
            push(candidate, results)
            trim results to efSearch

return best k from results
KnobWhen paidIncrease itCost
MBuild and storageMore graph connectivity; often better recall on difficult dataMore adjacency memory, build work, and distance checks
efConstructionBuild / insertBetter candidate search while choosing edgesSlower indexing; often a better graph
efSearchEvery queryExplore a wider layer-0 frontier; usually better recallHigher latency and CPU; should be at least k

Implementations expose these names with small variations. Faiss documents M, efConstruction, and efSearch; pgvector defaults to m=16, ef_construction=64, and ef_search=40 in its current documentation.[4][6]

Strengths and failure modes

Why teams choose it

High recall at low latency, no centroid-training phase, incremental insertion, and a direct search-time quality knob. It is often an excellent default when the graph and vectors fit the memory hierarchy.

What bites

Graph links consume memory. Deletes and updates can require tombstones or rebuilding. Selective filters can disconnect the useful path or leave too few acceptable candidates.

Filtering changes graph search. Post-filtering may return fewer than k hits. Integrated filtering may force wider exploration or switch to exact search over a small filtered set. Elasticsearch documents both adaptive behaviors; pgvector offers iterative scans to continue until enough filtered results are found.[8][6]

IVF: search selected cells

An inverted file index learns coarse centroids, assigns each vector to a centroid's list, and probes only the lists nearest the query. The skipped lists provide the speedup; a missed neighboring cell causes the approximation error.[4]

Build and query mechanics

# Training
centroids = kmeans(training_vectors, nlist)
for vector in database:
    list_id = argmin(distance(vector, centroid) for centroid in centroids)
    inverted_lists[list_id].append(vector_id, encoded_vector)

# Query
probe_ids = nearest_centroids(query, nprobe)
candidates = concatenate(inverted_lists[id] for id in probe_ids)
return top_k(score(query, candidate) for candidate in candidates)

As a rough first approximation, IVF scans nprobe / nlist of the database, though uneven cluster populations make the true fraction larger or smaller. Increasing nprobe improves recall and costs latency. Increasing nlist creates smaller lists but raises training, assignment, and centroid-search costs.[4]

“Inverted” has two meanings. A lexical inverted index maps terms to document posting lists. IVF maps learned vector-space cells to vector IDs or codes. Both reverse “item → bucket” into “bucket → items,” but their buckets and scoring are different. Hybrid RAG often uses both.

Product quantization: compress the payload

IVF decides where to look. Product quantization decides how cheaply to store and compare what is there. Split a d-dimensional vector into m subvectors. Train a small codebook in each subspace. Replace each subvector with its nearest codeword ID.

x = [x¹ | x² | … | xᵐ] → code(x) = [c₁, c₂, …, cₘ]

With 256 centroids per subspace, each code is one byte. A 1,536-dimensional float32 vector takes 6,144 bytes; a 96-subquantizer code takes 96 bytes, plus IDs and codebooks. Approximate distance computation precomputes query-to-codeword distances, then sums m table lookups per candidate. Faiss describes PQ as lossy compression that supports distance computation in the compressed domain.[1]

When IVF-style designs win

They are attractive when memory is constrained, GPU batch throughput matters, the corpus changes in rebuild-friendly batches, or the scale makes a fully resident graph expensive. They demand representative training data and monitoring for cluster imbalance and distribution drift. HNSW usually offers a stronger speed-recall point when memory is available; current pgvector documentation states that its HNSW implementation uses more memory and builds more slowly than IVFFlat, while providing better query performance.[6]

Engineer retrieval as a funnel

In RAG, ANN recall is necessary but insufficient. The system must retrieve answer-bearing chunks, respect access controls, avoid redundant context, and do so within a latency and token budget.

A worked retrieval flow

  1. Chunk documents at semantic boundaries and preserve parent ID, offsets, title, source, tenant, ACL, timestamps, and embedding version.
  2. Embed chunks and queries with the same model and preprocessing. Normalize if required by the metric contract.
  3. Apply hard authorization and tenancy constraints. Never rely on semantic similarity for access control.
  4. Retrieve a generous candidate set, for example dense C=100 plus lexical C=100. Tune HNSW efSearch or IVF nprobe against candidate recall.
  5. Fuse rankings, then rerank perhaps R=40 passages with a cross-encoder or task-specific scorer.
  6. Collapse duplicate or adjacent chunks, diversify across sources, and pack the best k within the model's context budget.

Index choice by constraint

Flat first
Use for small or heavily filtered corpora, low query counts, and ground truth. Index build cost may not amortize when searches are rare.[4]
HNSW
Choose when high recall and low online latency matter, memory can hold vectors plus graph, and incremental inserts are important.
IVF-Flat
Choose when training is acceptable, batch/GPU search matters, and you want partition pruning without lossy vector codes.
IVF-PQ
Choose when scale or memory dominates and reranking can recover final precision.
Disk-aware graph
Choose when the full graph or vectors cannot live in RAM. DiskANN demonstrated billion-point search on a single SSD-backed node, though its published benchmark numbers are hardware and dataset specific.[7]

Production checklist that changes outcomes

Version everything

Embedding model, dimensions, normalization, metric, chunking policy, index build, and corpus snapshot.

Measure two recalls

ANN recall against exact neighbors, then retrieval recall against answer-bearing judgments. They answer different questions.

Test filters

Benchmark realistic selectivities and ACL patterns. Filtering can reverse the apparent winner between exact, HNSW, and partitions.

Budget fan-out

Each shard may produce local candidates before global merge. More shards can raise latency and require larger candidate pools.

Plan rebuilds

Test model migrations, backups, compaction, tombstones, disaster recovery, and how long a full reindex actually takes.

Hybridize deliberately

Dense and lexical retrieval cover different failure modes. Fuse ranks or calibrated scores before reranking, and evaluate the combination.

A useful starting experiment: build a flat baseline and HNSW on the same snapshot. Sweep efSearch across at least five values under realistic concurrency and filters. Plot p95 latency against recall@50, then run the top three operating points through the same reranker and answer-quality evaluation. Add IVF-PQ only when that plot reveals a memory or throughput problem it can solve.
